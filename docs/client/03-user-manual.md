# Document 03 — User Manual

Step-by-step guidance for each implemented module, written from the perspective of the person using it day to day.

## 3.1 Admission

Admission is where a new (or returning) student's record is created. Two fields are commonly confused and must always be kept separate:

- **Registration ID** — Generated automatically by the system the moment a student is created. Permanent — it never changes, even if the student switches batch, course, or has their roll number corrected. This is the student's true, unique identity in LaraLMS.
- **Roll Number** — Typed in by the Admin (or supplied via Excel on bulk import). This is the coaching centre's own academic roll and can be corrected later if entered wrong — it is never used as the student's permanent identity internally.

1. **Student & guardian details** — name, mobile, date of birth, blood group, roll number, guardian name & mobile.
2. **Course selection** — choosing a Course pulls its configured fee automatically; this is a locked, one-time snapshot for this student — changing the Course's fee later in Settings never rewrites an already-admitted student's total.
3. **Fee calculation** — Total Course Fee (from the Course) + Admission Fee (from the current Settings value, also snapshotted) − any Discount entered = the student's starting total due.
4. **Optional first payment** — if an amount is paid at admission, it is recorded as a real payment (not just a number typed into the student record), so it appears immediately in Fee Management and gets its own receipt.
5. **Batch assignment** — the student can be placed into a Batch at admission or afterward from Batch Management.

## 3.2 Bulk Excel Admission

For admitting many students at once from an existing spreadsheet.

1. **Download the template** — a ready-made Excel file with the correct column headers.
2. **Fill it in.** The Course for the whole import batch is chosen once, up front, for the session — not per row.
3. **Upload** — the system parses every row and checks it against existing records for duplicate phone numbers and roll numbers, and flags anything that looks like a mismatch against the master list of HSC institutions.
4. **Preview** — every row is shown with its validation result before anything is saved to the real student list.
5. **Approve or reject, row by row** — approving a row creates that student exactly as if it had been admitted one at a time (same Registration ID generation, same fee logic); rejecting a row discards it. Nothing is created automatically just from uploading — approval is a deliberate, per-row action.
6. **Import history** — every upload session is kept so the office can see what was imported, by whom, and when.

> **Important:** whatever column in the spreadsheet is labelled as the coaching's own registration/roll number becomes the student's **Roll Number**, never the Registration ID — the Registration ID is always generated by the system, never taken from a spreadsheet.

## 3.3 Student Management

- **Search & filters** — by name/roll/registration ID/mobile (free text), course, batch, HSC institution, gender, division/district, due status, and "birthday today".
- **List order** — every student list in the system, including this one, is sorted by Roll Number in true numeric order (1, 2, 9, 10, 11 — not the text order 1, 10, 11, 2, 9).
- **Student Profile** shows: admin-set identity fields (read-only to the student), guardian information, HSC/SSC academic background, full payment history, current batch, and a profile-completion percentage that tracks how much of the optional information has been filled in.

## 3.4 Batch Management

1. **Create a batch** with a name, its Course, meeting days, time, room, start date, and a Batch Director.
2. **Assign students** — add existing (unassigned) students into the batch.
3. **Transfer** — moving a student to a different batch is a dedicated action, not a plain edit; a new roll number can optionally be set for the new batch, and the student's attendance/result/payment history is preserved unchanged.
4. **Withdraw** — removes a student from a batch (with a reason) without deleting the student record.

## 3.5 Staff Management

Staff types are Admin, Teacher, Staff, and Batch Director. Only **Admin-type** staff get a password-based login into the Admin Panel; every other staff type logs into the separate Staff Portal using their mobile number and a Staff ID (no password).

1. **Add a new staff member** — name, mobile, Staff ID, staff type, salary, join date.
2. **If the type is Admin**, a Password and Confirm Password field appears — a real login is created immediately, always, as part of the same action (there is no separate "create login later" step).
3. **Module access** — while creating (or editing) an Admin, a checklist lets you choose exactly which parts of the system that Admin can use (Students, Fees, Staff, Reports, etc.). Everything is allowed by default; unchecking a module removes it from that Admin's sidebar and blocks it on the server too.
4. **Editing or removing an existing Admin**, or resetting their password, is restricted to the original Super Admin account only — a regular Admin will see these options unavailable on another Admin's row.
5. **Changing your own password** — any logged-in user (Admin, Batch Director, or Student) can change their own password at any time from the account menu in the top bar ("Change Password"). *(Added in v1.1.)*
6. **Forced password change** — if the Super Admin resets your password, or your account was created without a password being set for it, the next time you log in you'll see a full-screen prompt requiring you to set a new password before you can use the rest of the system. This cannot be skipped or dismissed except by logging out. *(Added in v1.1 — see Document 08 for why this matters.)*

## 3.6 Fees & Payment Management

- **Due list** — every student with an outstanding balance, sorted by roll number, filterable by fee type.
- **Add Payment** — pick a student (search by name, roll, registration ID, or mobile), choose a fee type, payment method, amount, and date; the dialog guards against an accidental double-click creating two identical payments.
- **Payment methods** are a configurable list (e.g. Cash, bKash, Bank) managed in Settings, not hard-coded.
- **Payment history** shows receipt number, date, student, fee type, amount, discount/fine if any, and method for every payment, with a link to print/view its receipt.
- Every payment gets a unique **receipt number** generated automatically in the format configured in Settings (a prefix, a zero-padded sequence number, optionally resetting every year).

## 3.7 Payment Receipt

Each payment has its own dedicated, print-ready receipt page (opened separately from the main dashboard, with no sidebar/menu on it — ready to hand straight to a printer).

A receipt shows: the institution's name/logo/address/phone (from Settings), the receipt number, the student's **Registration ID and Roll Number as two separate, clearly labelled fields** (never merged or substituted for one another), the course and batch, the amount paid, the payment method and date, and the student's current remaining due. Print layout (paper size, margins, footer text, whether the logo appears) is configurable in Settings.

## 3.8 Admission Result

A separate module for matching official admission-test results (imported as a PDF) against the coaching centre's own list of applicants/students, so the office can see at a glance who from their admission-coaching batch actually got in, and where.

1. **Upload** the official result PDF.
2. **Preview** the parsed rows before anything is saved.
3. **Confirm / process** the match against the coaching's own admission roll numbers.
4. **Review** in Result Management-style summary and per-student stats (added/missing).

> Access to this whole module is controlled by a single dedicated permission (**Admission Result**), separate from every other module — see Document 04 for exactly what this does and doesn't affect.

## 3.9 Result Entry & Result Management

A Batch Director enters marks for their own batch, one subject/lecture/date at a time; attendance for that same session is recorded in the very same screen — there is no separate attendance step for a Batch Director.

- **Save Result** — stores the marks and attendance only. No SMS is sent. Safe to click repeatedly while still entering marks.
- **Send Result** — saves (the same save as above) and then texts each present guardian using a configurable message template. A student without a guardian mobile number on file is skipped and reported, not silently dropped.
- **SMS template** supports variables such as student name, roll, registration ID, subject, marks, percentage, grade, and pass/fail — either the coaching's global default template (Settings) or a Batch Director's own personal template.
- A failed SMS (bad number, gateway error) can be **retried individually** without re-saving or re-sending to everyone else.
- **Result Management** (Admin and Director) shows the full roll-sorted list of every student's overall result, a top-10 performers ranking, and a full exam-by-exam batch matrix.

## 3.10 Attendance

Attendance is captured as part of Result Entry (see above) for Batch Directors — there is no separate manual attendance-taking screen for them. The Admin's Attendance dashboard shows today/yesterday/this-week/this-month percentages, a daily present/absent breakdown, and a top-10 attendance ranking, filterable by batch and date range.

## 3.11 Material Management

This is a **coaching-material distribution system** — printed sheets, notes, model tests, question banks — not a traditional book-lending library. Nothing is "borrowed and returned"; a material is distributed to a student and that's a permanent record.

- **Material Types** (Lecture Sheet, Class Note, Model Test, etc.) are a configurable list.
- **Stock** is tracked per material with in/out stock-movement records.
- **Distribution** to a student can be free or paid; a paid distribution creates a real payment automatically, the same way an admission-time payment does.
- A configurable rule (allow / warn / block) controls what happens if the same material is distributed to the same student twice.
- Full distribution history is kept per student and per material, and feeds the Material Distribution report.

## 3.12 Branch & Branch Ledger

A Branch is a shared reference record (name, address, contact) used across Accounts and Reports for multi-location coaching centres. The **Branch Ledger** is a simple running tally per branch — money or material *sent to* the branch is logged as an expense, money *received back from* the branch is logged as income, and the system computes a running due balance (expense − income) per branch. It is separate from, and does not automatically post into, the main Accounts income/expense records, though both can be filtered by branch.

## 3.13 Reports

Every report below can be **printed** or exported to **Excel** or **PDF** from the same toolbar.

| Report | Shows | Filters |
|---|---|---|
| Admission | Student list with admission type (new/repeat) and date | Session, Course, Batch, date range |
| Fee Collection | Every payment received with totals | Date range, Course, Batch |
| Due | Students with an outstanding balance, largest first | None |
| Attendance | Per-student present/absent/percentage | Batch, date range |
| Result | Exam-by-exam marks with class average/max/min/pass-rate | Subject, Lecture, Exam *(the on-screen Course filter does not currently affect the results — see Document 06)* |
| Material Distribution | Per-material stock, distributed, and remaining totals | None |
| Staff | Staff list with salary and (for Batch Directors) 30-day batch attendance | None |
| Branch Ledger | Per-branch expense/income/due totals | None |

## 3.14 Notice Management

An Admin creates a notice with a title, description, priority (Normal/Important/Urgent), publish and expiry dates, and can pin it to the top. A notice can be targeted at Everyone, a specific Course, or a specific Batch — these three targeting options work end-to-end and are visible to Students today. (Director- and Staff-targeted notices exist in the data model but are not yet surfaced on any screen — see Document 06.)

## 3.15 Public Pages

**Public Student Information** — A visitor with no account can search for a student by Registration ID, phone number, or name. The Admin decides, in Settings, which of these three search methods are switched on, and which fields of a matched student (name, course, batch, attendance summary, etc.) are actually shown. Searches are rate-limited per visitor to prevent abuse.

**Public Marksheet** — A visitor can look up an individual result by Roll Number (within a date range) or view a whole batch's published result sheet. Both are switched on independently in Settings, can be restricted to only "published" exams, and are rate-limited the same way.

## 3.16 Student Portal

A student logs in with just their mobile number and current roll number — no password. Everything in the portal is the student's own data only:

- **Dashboard** — attendance %, total paid/due, latest result, course & batch summary.
- **Profile** — office-entered details shown read-only (name, Registration ID, roll, guardian mobile, etc.), plus a section the student can fill in themselves (address, guardian occupation/relation, HSC/SSC academic background), with a completion-percentage indicator.
- **Attendance** and **Results** — read-only history.
- **Payments** — fee summary and payment history with receipt links.
- **Materials** — their own distribution history.
- **Notices** — notices targeted at them.
- **Video Classes** — see Document 02's note on the current local-only limitation of this feature.

## 3.17 Settings

Settings is organised into sections, each controlling a distinct part of the system:

| Section | Controls |
|---|---|
| Institution | Name, logo, address, phone/email/website, currency symbol, date format, receipt number format (prefix / digits / yearly reset), print/PDF options (paper size, footer text, signature label, logo on documents). |
| Academic | Sessions, Courses (incl. fee), Subjects, Lectures — the full academic hierarchy — and the default session. |
| Student | System ID prefix (affects newly-created Registration IDs only) and Roll Number scope (whether a roll must be unique per-batch, per-course, or system-wide). |
| Result | Default exam duration, passing percentage, grade scale (percent bands to letter grades), whether questions shuffle, whether results publish automatically. |
| Finance | Admission fee amount and the list of accepted payment methods. |
| Material | Material Types list, duplicate-distribution rule, default minimum-stock suggestion. |
| Public | Public Student Info (on/off, search methods, visible fields) and Public Marksheet (on/off, individual/batch toggles, visible fields, published-only requirement). |
| Audit Log | A read-only trail of every settings change made, by whom and when. |
